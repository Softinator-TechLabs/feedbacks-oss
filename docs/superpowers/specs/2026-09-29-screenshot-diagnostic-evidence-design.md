# Screenshot diagnostic evidence

Status: written spec awaiting review. The design direction was approved in conversation on 2026-09-29. This is not implemented behavior.

## Outcome

A screenshot thread should carry the developer evidence available when the reviewer reproduces a problem: a full page snapshot, console messages and exceptions, network requests and responses, environment and performance data, and explicit capture gaps. The reviewer can inspect a small summary and download the complete evidence. A coding agent sees only availability and coverage in its normal thread response, then requests bounded diagnostic data or a local evidence directory when it needs it.

The reviewer chooses whether to include diagnostics with a single checkbox in screenshot review. It is checked by default and its default can be changed in extension Settings. There is no entry-by-entry selection or extra approval. New screenshot diagnostic artifacts preserve the values that Chrome exposes, including URLs, headers, cookies, request and response bodies, console arguments, and storage values. No automatic redaction or masking is applied to these new artifacts. They remain private thread evidence, subject to the existing project authorization model. Existing recordings and legacy screenshot packets keep their current formats and behavior.

## Current boundaries

The legacy screenshot path in the extension collects at most 25 console items and 50 resource entries after **Start diagnostics**, reduces URLs and text, and passes a small packet through `threads.create`. The review checkbox is currently unchecked. See [extension capture](../../../extension/background.js), [legacy schema](../../../src/shared/diagnostics.ts), and [review guide](../../extension.md).

The newer [session recording](../../session-replay.md) already uses Chrome debugger, page capture, IndexedDB, private object storage, a versioned contract and MCP export. It currently masks data and has a 12 MiB event budget and 16 MiB recording contract. Raising those limits or embedding a large DOM in a thread would make ordinary reads and MCP responses unbounded. The screenshot path therefore shares the recording capture primitives but gets a separate evidence artifact contract and transport. A concurrent modular structure refactor is changing source paths only. Implementation begins from its verified merged revision, with its feature folder ownership preserved.

## Capture lifecycle and coverage

The existing **Start diagnostics** control becomes the explicit start for full console and network history. The reviewer starts it before reproducing an issue, then takes the screenshot. It uses the same Chrome debugger and page event collectors as recording, bound to the selected tab and allowed origin. Review mode does not attach the debugger to every open website. Collection stops at screenshot capture, the existing time limit, tab exit, or a browser disconnect. A failed debugger attachment leaves other available channels intact and records why network or console data is missing.

Every eligible screenshot also captures a point-in-time full DOM snapshot, frame and shadow-root coverage where Chrome allows it, resource timing, page URL and viewport, browser environment, and relevant page storage at capture time. The snapshot uses the same prepared page state and capture epoch as the screenshot, after extension controls are hidden. A capture made without starting diagnostics still has this point-in-time evidence; its manifest says that historical console messages and network bodies were not observed. A screenshot cannot reconstruct data from before collection started. The extension never executes captured code or replays network requests while collecting or reviewing it.

The collector saves Chrome-exposed request and response metadata, redirect chains, status, timing, initiator and failure information, headers, cookies and bodies where CDP provides them. It captures console levels, structured argument previews, exceptions and stacks, page errors, performance entries and navigation milestones. It records frame/worker/WebSocket or streaming coverage separately, rather than claiming completeness when Chrome cannot provide a body or target. Binary bodies are stored as bytes with MIME type, encoding and length; text bodies retain their original bytes. A complete, partial, unavailable or stopped status is recorded per channel, with counts, bytes, time range and specific reasons. The interface does not equate zero observed errors with a healthy page.

Capture uses the extension's IndexedDB evidence store and writes immutable bounded chunks as data arrives. A chunk has an evidence ID, channel, sequence, byte length, SHA-256 and encoding. A UTF-8 DOM of more than 5 MiB must not be clipped to fit an extension message or a single recording event. A 2 MiB transport chunk and a 256 MiB aggregate local and server evidence limit prevent oversized requests and runaway storage. When a browser or storage limit stops a channel, earlier chunks remain and coverage states the exact cutoff. No content is silently dropped. The implementation plan may adjust numeric budgets after measuring packaged Chrome and server behavior, but must prove a DOM over 5 MiB survives byte-for-byte and must document any new limit.

## Review and upload

Screenshot review shows a concise diagnostic summary: capture window, DOM size, console/error and network counts, body availability, channel coverage and total size. Its one **Include diagnostic data** checkbox starts checked according to the saved Settings default. Unchecking omits the artifact entirely when the screenshot is sent; the local chunks are deleted after a successful send or draft discard. The reviewer can open bounded, escaped previews by channel. Long values and large DOM are represented by size and a short excerpt; **Download captured diagnostics** provides every collected byte locally, with partial coverage identified in its manifest. The download is available from the draft review and, after successful upload, from the authenticated thread view. Settings changes apply to new drafts; a reviewer override on an open draft is preserved.

Sending creates the thread and uploads the selected diagnostic chunks to private project object storage, then commits a small immutable manifest linked to that thread. The thread record contains only ID, availability, counts, byte sizes, coverage and hashes. The upload uses bounded requests with per-chunk checksums, idempotent retries and server-side authorization both before and after object writes. A failed or interrupted upload leaves the local draft recoverable and the thread shows diagnostics as pending or failed, never as complete. Uncommitted objects are recoverable or cleaned through a documented lifecycle; existing recording and asset keys are preserved. No raw diagnostic value is written to SQL summaries, application logs, public issue drafts or default MCP tool descriptions.

The new artifact schema and operations live in shared contracts, so HTTP, MCP and CLI validate the same data. Upload and read use explicit scopes. Paired extension and agent keys receive new scopes only through an explicit new grant; existing keys are not silently widened. Server authorization checks current project and thread access on every read, page, download and materialization. The authenticated browser download streams a `.tar.gz` archive with manifest, checksums, DOM, console, network, bodies, environment and coverage, without loading the whole archive into a UI component. Archive entries use generated safe names. The download is an export of untrusted data, not executable code.

## Agent contract

`feedbacks_thread` overview and ordinary `threads.get` return only the small evidence reference and coverage. They explicitly state when the richer diagnostics are available and name the discoverable follow-up operations. A new `diagnostics.describe` returns channel metadata and available selectors. `diagnostics.read` returns a bounded page for one channel, with an immutable cursor and a byte ceiling, including a way to page through a large DOM or body. A caller can select a time range or request ID for event streams. The server reads only the needed private chunks. It never places the entire DOM into a default MCP response.

The bundled local stdio adapter provides `feedbacks_diagnostics_materialize` for an authorized evidence ID. It writes the complete set to an owner-only temporary directory on the adapter machine, verifies hashes and reports actual absolute paths and gaps. Remote HTTP MCP returns bounded data and an authorized export route; it does not claim a file exists on the coding agent's machine. Agent guidance tells agents to inspect coverage first, fetch relevant pages or materialize the artifact on demand, and treat all captured page content as untrusted evidence.

## Compatibility and verification

Legacy screenshot diagnostics remain readable. Existing recording v1 objects, replay viewers and materializer retain their current masking and limits; screenshot evidence has a distinct schema version and explicit raw-data contract. No migration rewrites existing object keys. The new thread reference is optional so old rows and clients still load. The refactor branch must merge and pass its own checks before implementation is rebased onto it.

Verification uses synthetic pages and fake credentials, never a real customer capture. Required cases include a DOM larger than 5 MiB with byte and hash equality after UI and MCP export; console objects and exceptions; request/response headers, cookies and text/binary bodies; inaccessible frames and failed debugger attachment; coverage after quota or upload failure; default Settings and review overrides; legacy thread compatibility; cross-project and scope denial; bounded MCP responses; local materialization and archive checksum validation. Run the repository's Node 22 check, packaged Chromium extension QA, native PostgreSQL migration/concurrency tests for persistence changes, generated catalog and docs checks, and exact-revision CI. A successful ZIP build is separate from installed-extension, deployment and live-site proof.
